        Problem

        Customers spend too much time searching for products in large supermarkets due to the lack of an efficient navigation system.

        Solution

        The system calculates an efficient route to every selected product and the nearest billing counter, then shows it both as a live route drawn on the store map and as dynamically generated step-by-step text guidance.

        🎓 Viva / Presentation Prep

        Tap a question to reveal a clear, confident answer.

        1. Why is A* Search used for this project?

        A* combines the actual distance already travelled, g(n), with an estimated distance to the destination, h(n). Because it always expands the node with the lowest f(n) = g(n) + h(n), it finds an efficient path toward the goal instead of blindly exploring in every direction, so it reaches the destination while checking far fewer nodes than an uninformed search.

        2. What does "heuristic" mean?

        A heuristic is an estimate or rule of thumb used to guide a search toward a goal faster, without needing to explore everything first. In A*, h(n) estimates how far a node is from the goal so the algorithm can prioritise the most promising nodes first.

        3. Why is Manhattan Distance a suitable heuristic here?

        The supermarket navigation only allows horizontal and vertical movement between walkable points - never diagonally - so Manhattan Distance (|x1−x2| + |y1−y2|) matches exactly how movement cost accumulates. It also never overestimates the true remaining distance, which is the admissibility property A* needs to guarantee the shortest path.

        4. Why isn't BFS used for the final implementation?

        BFS searches level by level with no sense of "direction" toward the goal, so on a large store graph it may explore many unnecessary locations before reaching the target. A* uses the heuristic to search purposefully toward the destination, so it's far more efficient while still guaranteeing the shortest path when the heuristic is admissible - which Manhattan Distance is here.

        5. Why isn't DFS used for the final implementation?

        DFS does not guarantee the shortest path at all - it can commit to a long branch of the graph before ever finding the goal, and has no concept of cost. A* always tracks g(n), h(n) and f(n) for every node it considers, so it provably returns the optimal route instead of just "a" route.

        6. How is the supermarket represented internally?

        As a graph/grid (see data/supermarketMap.js): a 2D array where each cell is 0 (walkable floor) or 1 (a shelf/wall). Eleven rectangular sections (Grocery, Masala, Snacks, Dairy, ...) are laid out in a table with walking corridors between them, and the Entrance, every product, and all four Billing Counters are each pinned to a specific (x, y) coordinate. The map you see on screen is a styled drawing on top of this graph - the raw grid itself is never shown to the customer.

        7. How are shelf obstacles handled?

        Every section has a shelf-rack obstacle carved through its middle. When A* looks at a node's neighbours (getWalkableNeighbors), it only accepts neighbouring cells that are inside the grid AND whose value is 0. A cell marked 1 is never offered as a neighbour, so the algorithm is automatically forced to route around it via the open aisles and corridors - obstacles are never special-cased, they just make certain edges of the graph unavailable.

        8. How are the route line and text instructions generated dynamically?

        For multiple products, a nearest-neighbour rule first decides a sensible visiting order from the Entrance, and the nearest suitable Billing Counter is chosen by comparing the real A* distance to each of the four counters. A* then computes the shortest path for every leg of the trip, and all the legs are joined into one path. That single list of coordinates is used twice: mapRenderer.js converts it straight into the SVG route line and arrows, and navigationInstructions.js walks through the same coordinates, grouping consecutive same-direction moves and detecting left/right turns, to write the turn-by-turn text - so the map and the text are always guaranteed to describe the exact same route, because they come from the exact same A* output.
